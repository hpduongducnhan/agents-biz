D1 — Template + module mẫu + công cụ tạo module · 2026-10-14 #

Quyết định: repo là một template chạy được như app thật, kèm một module mẫu chạy trọn các tầng và lệnh / skill tạo module mới. App mới = copy template + đổi tên. Lý do: mỗi app sau chỉ thêm nghiệp vụ; module mẫu là khuôn cho scaffold. Đã loại: chỉ có khung (phải tự dò cách làm); một repo chung cho nhiều app (các app dính chặt nhau khi deploy / nâng cấp).

D2 — Giữ nguyên stack của dự án nguồn · 2026-10-14 #

Quyết định: Python 3.13 FastAPI + FastStream / taskiq trên RabbitMQ, service realtime Node + Socket.IO, React 19 + Vite + TanStack Query + Zustand + Tailwind 4 + Radix, Postgres + Redis (+ Mongo theo cờ), LangChain v1 / LangGraph, deploy Coolify. Lý do: đã chạy thật trên prod, rủi ro thấp nhất. Đã loại: bỏ RabbitMQ / Mongo, gộp realtime vào Python (phải viết lại, mất phần đã chạy thật).

D3 — Tenant đơn giản: chỉ để tách dữ liệu khách hàng · 2026-10-14 #

Quyết định: tenant là ranh giới dữ liệu; agent giữ một bộ như dự án nguồn dùng chung cho mọi tenant. Chủ dự án chỉnh lại sau câu trả lời ban đầu "workspace, quyền theo từng workspace". Lý do: hệ đa tenant nhiều tầng quá phức tạp để tích hợp agent; nhu cầu chính là tách dữ liệu từng khách hàng. Đã loại: user ở nhiều workspace với role theo workspace; cấu hình agent riêng từng tenant.

D4 — Web ưu tiên điện thoại + PWA, không native · 2026-10-14 #

Quyết định: một codebase web, thiết kế 375px trước, cài được lên màn hình chính, Web Push. Đã loại: chuẩn bị sẵn cho app native; làm app Expo ngay.

D5 — Đăng nhập: email + mật khẩu, Google, lời mời · 2026-10-14 #

Quyết định: email + mật khẩu (xác thực email, quên mật khẩu), Google OAuth, mời vào tenant bằng email hoặc link. Đã loại: magic link / OTP (để sau).

D6 — Mang sang đầy đủ hệ thống tài liệu + rule của dự án nguồn · 2026-10-14 #

Quyết định: giữ rule R1–R28 + rule riêng backend / frontend, nhật ký D<n>, plan theo SP (package R25), HLD + sơ đồ archify, make docs / docs-check; viết lại ví dụ, bỏ nội dung nghiệp vụ của dự án nguồn. Đã loại: bản rút gọn (mất phần kiểm tự động link / backlink / số dòng).

D7 — Đa ngôn ngữ, mặc định vi, có en · 2026-10-14 #

Quyết định: mọi chuỗi FE qua t(), từ điển [vi, en]; mail theo users.locale; agent trả lời theo ngôn ngữ của user. Đã loại: chỉ tiếng Việt; chỉ tiếng Anh.

D8 — Module mẫu: Tasks · 2026-10-14 #

Quyết định: quản lý công việc (trạng thái, ưu tiên, hạn, người làm, bình luận, nhắc hạn, chuyên gia agent). Lý do: thể hiện đủ mọi tầng: CRUD, quyền, realtime, việc nền, thông báo, agent + duyệt. Đã loại: Notes (ít realtime / việc nền); Flashcard (ít phân quyền).

D9 — Tên cố định bw + make new-app đổi tên · 2026-10-14 #

Quyết định: template mang tên cố định (BizWithAgents / slug bizwithagents / tiền tố bw, cổng local 8201–8204, container 16811–16813); make new-app chép + đổi tên một lần. Lý do: template tự chạy và test được như app thật; code giữ chuỗi literal; hai app dùng chung hạ tầng không đụng tiền tố. Đã loại: tên đọc từ env lúc chạy (chuỗi ghép động, khó grep); cookiecutter (template không chạy thẳng được).

D10 — Mỗi user thuộc đúng một tenant · 2026-10-14 #

Quyết định: users.tenant_id NOT NULL, claim tid trong JWT; không có bộ chuyển tenant; một email chỉ ở một tenant. Lý do: agent và tool không phải biết tenant — lấy từ người đang chat. Đã loại: user ở nhiều tenant + role theo tenant (cần tham số tenant ở tool, bộ chuyển ở UI).

D11 — Tách dữ liệu bằng bộ lọc tự động ở session · 2026-10-14 #

Quyết định: model module kế thừa TenantScoped; session của op / việc nền mang tenant_id; SQLAlchemy do_orm_execute + with_loader_criteria tự thêm điều kiện, before_flush tự gán / kiểm; xem chéo chỉ qua ctx.cross_tenant() của superadmin. Test luật cấm SQL thô trên bảng tenant. Lý do: quên lọc vẫn an toàn; không thêm gì vào migration; một choke-point. Đã loại: tự lọc từng query (quên là lộ dữ liệu); Postgres RLS (policy mỗi bảng, khó gỡ lỗi); schema / DB riêng mỗi tenant (nặng).

D12 — signup_mode quyết định người đăng ký vào tenant nào · 2026-10-14 #

Quyết định: default_tenant (mặc định — chạy như dự án nguồn) · new_tenant (mỗi người đăng ký có tenant riêng, là admin) · invite_only. Lời mời (email / link) chạy ở mọi chế độ. Role dùng chung mọi tenant, chỉ superadmin tạo role mới. Đã loại: role riêng từng tenant (để TẦM NHÌN).

D13 — Realtime: phòng tenant:<tid> · 2026-10-14 #

Quyết định: socket join phòng tenant lúc bắt tay theo claim tid; ctx.invalidate(keys, tenant=True) phát một message; sự kiện riêng vẫn tới user:<id>. Lý do: user không đổi tenant nên không có join / leave động; data:changed chỉ mang key nên phát cả tenant không lộ dữ liệu. Đã loại: gửi tới từng user:<id> (N message, phải tra danh sách user).

D14 — Mail: console + smtp · 2026-10-14 #

D27 — Tạo app sau khi clone: đổi tên tại chỗ, giữ lịch sử, remote template · 2026-10-15 · Claude tự quyết theo yêu cầu chủ dự án #

D29 — Kéo bản sửa của template về app đã đổi tên: make template-sync · 2026-10-15 · chủ dự án duyệt đề xuất sau review SP6 #

Phương án File mới của template vào app mang tên app Xung đột giả ở dòng đã đổi tên Lần sau tính từ Công sức
make template-sync: đổi tên bản template đã đồng bộ + bản mới bằng luật của init-app, cherry-pick phần chênh ✓ ✗ template_commit trong .template.json ~1 buổi
git merge template/main + grep tay ✗ (lọt khi quên grep, git không báo) ✓ mọi dòng template sửa có tên merge-base 0
Chỉ playbook hướng dẫn sửa tay ✗ ✓ — thấp

→ Chọn make template-sync: app ghi .template.json (tham số đổi tên + template_commit) lúc init-app / new-app; lệnh lấy new_app.py + template_sync.py mới nhất từ remote template (git archive → debug/, luật đổi tên luôn mới), dựng hai cây đã đổi tên, cherry-pick lên app → xung đột chỉ còn ở chỗ app và template cùng sửa; chặn khi cây chưa sạch / đang dở; cuối cùng kiểm còn tên template ở file vừa đổi (R11 — không âm thầm). App tạo bằng new-app DEST dùng được sau git remote add template <url>. new-app-check đi đường clone → init-app → template có bản sửa → make template-sync. Đã cân nhắc: merge thẳng (tên template lọt qua file mới mà không xung đột; xung đột ở mọi dòng có tên); merge commit đã đổi tên thay cherry-pick (cần lịch sử chung giả, khó đọc hơn). Kèm theo (review SP6): make new-app tự kiểm công cụ + cài backend/.venv (bản clone mới chưa có → not found); init-app / new-app kiểm công cụ ở chế độ shared (đổi tên không cần Docker); README.md gốc cho người mở repo trên GitHub.

D30 — Repo public: quét secret + tên riêng trước push, tài liệu không ghi hạ tầng thật · 2026-10-15 · chủ dự án chốt phạm vi dọn; công cụ Claude tự quyết (uỷ quyền R28) #

Công cụ Quét lịch sử git Kiểm key còn sống Chạy offline Cài
gitleaks + trufflehog (tuỳ chọn) ✓ ✓ (trufflehog) ✓ (gitleaks) 1 binary mỗi công cụ, hoặc Docker
chỉ trufflehog ✓ ✓ ✗ (luật generic yếu, ít bắt secret dạng KEY = "…") 1 binary
detect-secrets (Yelp) ✗ (theo baseline file) ✗ ✓ Python, baseline phải commit
chỉ GitHub secret scanning ✓ sau khi push một phần — 0 — nhưng chỉ báo sau khi đã lộ

→ Chọn gitleaks làm bước bắt buộc trong make ci, trufflehog tuỳ chọn: gitleaks bắt cả secret dạng generic (lần quét đầu báo 10 chỗ — đều là giá trị giả trong test / PEM giữ chỗ trong tài liệu, đã ghi ngoại lệ hẹp), chạy offline trước push; trufflehog chỉ báo key còn sống nên ít báo sai. Thêm bước tên riêng đọc .secrets/private-terms.txt — danh sách nằm ngoài repo nên chặn được tên dự án khác / domain / IP mà không phải ghi chúng vào code (test_no_source_refs.py thôi chứa tên dự án nguồn). Phạm vi dọn (chủ dự án chốt): tên dự án nguồn → "dự án nguồn"; domain → <domain> / example.com, make smoke-prod lấy PUBLIC_URL từ .secrets/coolify.env; IP / user DB / container / Redis db của app khác → chỗ giữ, giá trị thật ở .secrets/. Lịch sử git làm lại từ một commit (repo cũ còn email công ty và tên riêng ở các commit trước) — template_commit của app tạo trước mốc này không còn trong remote, make template-sync của các app đó phải đặt lại .template.json. Đã cân nhắc: viết lại lịch sử bằng git filter-repo (giữ 8 commit nhưng phải lọc cả nội dung lẫn email, dễ sót); chỉ dựa GitHub secret scanning (báo sau khi đã public).

D31 — Không port nghiệp vụ / realtime sang Go, giữ Python + Node · 2026-10-15 · chủ dự án chốt #

Tải mục tiêu ~10k user, ~2k DAU. Ước lượng (giả định ~100 request / người / ngày): trung bình ~2–3 req/s, giờ cao điểm ~8 → ~25 req/s, ~200–500 socket đồng thời; lượt chat chủ yếu chờ LLM (I/O).

Phương án Công sức Dư tải ở 2k DAU Lõi (RBAC / tenant / envelope) Agent gọi nghiệp vụ Rủi ro
Giữ Python + Node, đo rồi chỉnh giờ – ngày ≥ 10× 1 bản cùng process (@operation(agent=True)) thấp
Nghiệp vụ + realtime Go, agent Python nhiều tuần (~12k dòng app + test) lớn hơn, không cần tới 2 bản (35 op của agent vẫn cần lõi) hoặc Go làm cửa duy nhất qua mạng (danh mục op + gọi thay user) cao
Chỉ realtime sang Go ~0,8k dòng TS như trên 1 bản cùng process thấp, lợi ít

→ Chọn giữ stack: ở quy mô này nút cổ chai là truy vấn DB / index, pool kết nối, chi phí + rate limit LLM — đổi ngôn ngữ không giải quyết. Không tạo branch pythonnodejs / pygo. Xem lại khi đo thấy: CPU bw-api bão hoà dù API_WORKERS = số core mà p95 vẫn chậm; RAM cả stack vượt ngân sách server (thử gộp consumer / worker / scheduler vào một process trước); socket đồng thời hàng chục nghìn mỗi instance. Đo bằng load test (k6 / Locust) trên make dev-up. Đã cân nhắc: port toàn bộ kể cả agent sang Go (hệ AI của Go chưa trưởng thành, mất checkpointer / trace LangGraph).
